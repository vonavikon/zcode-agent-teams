# Ревью robustness: team.py + SKILL.md (Грабли)

Линза: Windows/Git Bash, конкурентный доступ, краевые случаи команд.

Пути файлов (далее короткие имена):
- team.py = C:/Repos/zcode-agent-teams/plugins/agent-teams/skills/agent-teams/scripts/team.py
- SKILL.md = C:/Repos/zcode-agent-teams/plugins/agent-teams/skills/agent-teams/SKILL.md

Сверка раздела «Грабли» (SKILL.md:72-78) с кодом — в конце, после findings.

## CRITICAL

### R-1. tasks.json — read-modify-write всего файла без межпроцессной блокировки, tmp-файл с фиксированным именем

team.py:43-50 (load_tasks/save_tasks), мутации в claim team.py:114→136 и verify team.py:146→154/160.

Лок в locks/ (team.py:122-134) защищает только повторный claim той же задачи. Само сохранение — загрузка всего tasks.json, правка, запись всего файла — ничем не сериализовано, а параллельные claim разных задач это штатный режим: лид спавнит тиммейтов одновременно (SKILL.md:23).

Сценарий потери: агент A (claim task-1) и агент B (claim task-2) читают один снапшот в team.py:114; B сохраняется первым (task-2=in_progress); A сохраняет свой снапшот — статус task-2 откатывается в pending, claim B стёрт. При этом events.jsonl содержит task_claimed для обоих, журнал и состояние расходятся. Никакого сообщения об ошибке нет ни у кого.

Вторая половина: tmp-файл один на всех (team.py:48, `tasks.json.tmp`). Два параллельных save_tasks пишут в один и тот же tmp — возможен интерливинг содержимого до replace либо FileNotFoundError, когда первый процесс уже перенёс файл, а второй делает replace.

Фикс:
1. Уникальное имя tmp: `tmp = d / f"tasks.json.tmp.{os.getpid()}.{uuid.uuid4().hex[:8]}"`.
2. Сериализация мутаций: командный лок (например, `locks/.tasks.lock` через os.open с O_CREAT|O_EXCL, спин-ретрай с таймаутом 5-10 с), захватываемый в claim/verify/message/read вокруг пары load→save. На Windows хватит O_EXCL-спина, msvcrt.locking не обязателен.

## MAJOR

### R-2. Mailbox: гонки read-modify-write молча теряют сообщения, включая фидбек VERIFY FAIL

team.py:163-170 (verify fail дописывает в ящик исполнителя), team.py:181-186 (message), team.py:198-202 (read: загрузка → отметка read → запись).

Сценарий потери: агент выполняет read и загрузил снапшот (team.py:198); параллельно verify fail дописал сообщение и сохранил (team.py:170); агент сохраняет свою копию (team.py:202) — сообщение верификатора удалено. Исполнитель не узнаёт о FAIL и висит в ожидании, цикл приёмки ломается без диагностики.

SKILL.md:77 предупреждает «mailbox — read-modify-write без локов: не давай двум агентам одновременно писать в один ящик, шлёт обычно лид». Предупреждение неполное: пишущих путей в самом движке два — message и verify-fail (team.py:163-170). Даже при дисциплине «шлёт только лид» верификатор с --verdict fail обходит правило, и гонка возможна между verify-fail и read исполнителя.

Фикс: хранить ящик как append-only JSONL (`inbox/<agent>.jsonl`, одна строка = одно сообщение, дописывание через open("a")); позицию «прочитано» держать отдельно (`inbox/<agent>.read` — ts или id последнего прочитанного). Тогда read ничего не переписывает, append не теряет сообщения. Минимальный вариант — накрыть операции с inbox тем же командным локом из R-1.

### R-3. Лок claim не освобождается никогда; после сбоя агента задача невосстанавливаема

team.py:122-134 — лок создаётся, но нигде в файле нет его удаления: verify pass (team.py:152-156) locks/ не трогает, команд release/takeover/unclaim нет (проверено grep по файлу).

Сценарий 1: процесс упал между os.open (team.py:124) и save_tasks (team.py:136). Статус остался pending, лок висит. Следующий claim навсегда падает с «заблокирована другим агентом» (team.py:132), восстановление — только ручное удаление файла.

Сценарий 2: агент умер после claim. Задача in_progress, статус не откатить: claim требует pending (team.py:116-117). Закрыть через verify можно, передать другому исполнителю — нет.

SKILL.md:26 обещает «Максимум 2 круга, дальше задачу забирает лид» — движком это не поддержано: команды забрать задачу не существует, лиду остаётся ручная правка tasks.json плюс удаление locks/<id>.lock, о чём документация не говорит.

Фикс: добавить команду `release --team --task --by <lead>` — снимает лок, ставит status=pending, опционально --reassign <agent>. Дополнительно удалять лок при verify pass. Для сценария 1 — детекция протухшего лока: claim при существующем локе со ts старше N часов пусть печатает предупреждение с именем владельца и подсказкой про release вместо глухого отказа.

### R-4. Windows: os.replace поверх tasks.json, открытого другим процессом, даёт PermissionError

team.py:50 (`tmp.replace(d / "tasks.json")`).

На Windows rename поверх файла, открытого другим процессом без FILE_SHARE_DELETE (обычный read_text в load_tasks, team.py:44), заканчивается WinError 5. Параллельные load/save у нескольких агентов — прямой путь уронить claim или verify необработанным исключением; антивирус и индексатор расширяют окно.

Фикс: ретрай-цикл вокруг replace (10 попыток с паузой 50 мс, потом исключение с внятным текстом). Полное решение — командный лок из R-1: при сериализованных мутациях читателей в момент replace нет.

### R-5. events.jsonl: append из нескольких процессов без гарантии атомарности + жёсткий парсинг в langfuse

team.py:56-58 (open "a" + write + flush), team.py:235 (`json.loads(l)` по каждой строке без обработки ошибок).

На POSIX O_APPEND даёт атомарность коротких записей, на Windows такой гарантии нет — два одновременных append могут склеить или затереть строки. Битая строка появляется и после kill процесса в момент записи. Дальше одна повреждённая строка роняет весь экспорт: team.py:235 кидает необработанный JSONDecodeError в cmd_langfuse.

Фикс: в team.py:235 — парсить с try/except json.JSONDecodeError на строку, битые пропускать с предупреждением в stderr и счётчиком. Для log_event — писать под командным локом из R-1.

### R-6. Идентификаторы team/task/by/to/for без валидации попадают в пути файловой системы

team.py:37 (root/.agent-teams/<team>), team.py:98 (init), team.py:122 (locks/<task>.lock), team.py:163, 180, 194 (inbox/<agent>.json).

`--team ../other` заставит движок читать и писать каталог за пределами .agent-teams. Имя агента вида `nau:bot` или содержащее `/ \ * ? " < > |` даёт невалидное имя файла на Windows и необработанный OSError. init (team.py:77-81) проверяет только непустоту полей, не набор символов.

Фикс: единый предикат `re.fullmatch(r"[A-Za-z0-9][A-Za-z0-9._-]*", value)` для team, id задач, by, to, for в начале соответствующих команд; ту же маску проверять в init для id и assignee.

### R-8. Мёртвый статус «verifying»

team.py:148 допускает статус "verifying", но ни одна команда его не ставит (единственное вхождение в файле — сама проверка). Либо убрать из кортежа, либо добавить переход в verifying перед запуском верификатора.

### R-9. Лимит «максимум 2 круга» не enforce'ится движком

team.py:158 — verify fail просто инкрементирует rounds; соглашение о двух кругах живёт только в SKILL.md:26. Хотя бы печатать предупреждение при rounds >= 2, а после — подсказку передать задачу лиду через release из R-3.

### R-10. cmd_status падает целиком на одном битом mailbox

team.py:218 — json.loads без try в цикле по inbox/*.json. Один повреждённый файл (последствие R-7) ломает всю команду status.

Фикс: try/except на файл, вывод «mailbox <имя>: повреждён, пропущен».

### R-11. Гонка mkdir в init

team.py:99-102 — проверка d.exists() и mkdir разнесены. Два параллельных init дают второму необработанный FileExistsError вместо аккуратного сообщения об уже существующей команде.

Фикс: обернуть создание inbox/locks в try/except FileExistsError либо использовать exist_ok=True после собственной проверки каталога.

### R-12. Кодировка вывода в pipe на Windows

team.py:203 — read печатает json.dumps(..., ensure_ascii=False). На русской Windows stdout в pipe (Git Bash перехватывает вывод) кодируется cp1251: кириллица проходит, но любой символ вне cp1251 в тексте сообщения (эмодзи, CJK) даёт UnicodeEncodeError и обрушивает read.

Фикс: в main() вызвать `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` (Python 3.7+), либо печатать с ensure_ascii=True.

### R-13. read помечает сообщения прочитанными до фактической доставки

team.py:199-203 — отметка read и запись выполняются независимо от того, дошёл ли вывод до получателя. Если субагент оборвался после read, сообщения уже помечены и при следующем опросе не вернутся.

Фикс: режим `--peek` (печать без отметки) плюс явное `--ack <id>`, либо отмечать прочитанным только то, что агент подтвердил.
