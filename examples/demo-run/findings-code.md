# Ревью team.py — линза correctness (init/claim/verify/message/read/status)

Файл: `plugins/agent-teams/skills/agent-teams/scripts/team.py` (357 строк). Все номера строк и цитаты проверены чтением файла. Секции CRITICAL нет: на «счастливом» пути (один агент, последовательные команды) логика ошибок не даёт; самые тяжёлые проблемы — гонки и невосстановимые состояния при сбоях.

## CRITICAL

Не найдено.

## MAJOR

### M1. Гонка read-modify-write на tasks.json: потеря статусов соседних задач
team.py:114, 136 (claim); 146, 154, 160 (verify); 47-50 (save_tasks)

`cmd_claim` и `cmd_verify` работают по схеме «прочитал tasks.json в начале → записал в конце», между чтением и записью никакой блокировки. Сценарий: агент A и агент B одновременно забирают разные задачи. Оба успели выполнить `load_tasks` (строка 114) — оба видят все задачи `pending`. A создаёт lock, сохраняет (`save_tasks`, 136): задача A → `in_progress`. B создаёт свой lock, сохраняет свой экземпляр `data` (136): задача A молча откатывается в `pending`, задача B → `in_progress`. Итог: в tasks.json задача A = `pending`, но lock-файл A уже существует. Claim по ней больше не пройдёт (строка 125, «заблокирована другим агентом»), verify тоже (строка 148, «не в работе»). Задача встаёт намертво без ручного редактирования. Демо-сценарий запускает трёх агентов параллельно, так что окно между 114 и 136 реально достижимо.

Фикс: обернуть каждую команду, меняющую tasks.json, в лок вида `locks/.tasks.lock` (O_CREAT|O_EXCL с коротким retry-циклом, снять в finally), либо в `save_tasks` перед записью перечитывать файл и переносить изменения только своей задачи (merge), а не писать весь снимок целиком.

### M2. Гонка на mailbox-файлах: потеря сообщений, в том числе фидбека verify fail
team.py:163-170 (verify fail), 180-186 (message), 199-202 (read)

Все три места делают «прочитал mailbox → дописал/пометил → записал файл целиком» без блокировки. Два одновременных `message --to X` (например, verifier шлёт VERIFY FAIL, а тимлид — обычное сообщение) — выживает последняя запись, первое сообщение теряется бесшумно. Хуже с `cmd_read` (199-202): если между чтением (198) и записью (202) в файл кто-то дописал сообщение, оно затирается старым снимком — теряется вместе с попыткой доставки. Потеря VERIFY FAIL ломает цикл «круг 2» из промпта исполнителя: он просто не узнаёт о провале.

Фикс: тот же per-файл lock, что и в M1 (например, `locks/inbox-<agent>.lock`), либо единый lock команды вокруг любого изменения mailbox. Минимум — в `cmd_read` перечитывать файл перед записью и мержить сообщения, появившиеся после чтения.

### M3. Осиротевший lock: краш между os.open и save_tasks блокирует задачу навсегда
team.py:122-136

Lock создаётся на строке 124, статус в tasks.json меняется только на 136. Краш (Ctrl+C, диск, kill агента) между этими точками оставляет: lock есть, статус `pending`. Повторный claim того же агента упадёт на 125-132 с «заблокирована другим агентом: <собственное имя>». Команды снятия lock в скрипте нет: grep по unlink/remove/rmtree — пусто, в argparse (304-349) только init/claim/verify/message/read/status/langfuse. Восстановление только ручным удалением файла.

Фикс: добавить подкоманду `unlock --team --task --by` (снимает lock, если `--by` совпадает с owner из lock-файла, плюс `--force` для человека). Дополнительно можно писать owner claim в tasks.json (поле `claim_owner`) — тогда lock и статус расходятся заметно проще.

### M4. Имена team/agent/task не проверяются: выход за пределы каталога команды и OSError на Windows
team.py:98 (init, путь команды), 122 (имя lock-файла), 163, 180, 194 (имя mailbox-файла)

`--team`, `--to`, `--for`, `--by`, `--task` попадают в пути как есть. `--to "../evil"` записывает `inbox/../evil.json`, то есть `<team>/evil.json` — вне inbox; `--team "../x"` при init создаёт каталог за пределами `.agent-teams`. Инвариант «все файлы команды лежат в `.agent-teams/<team>/» никак не enforced. Отдельно: имя с символами `<>:"|?*` на Windows упадёт нечитаемым OSError-traceback, а не аккуратной ошибкой.

Фикс: валидировать все имена одним регулярным выражением в начале каждой команды (или через `type=` в argparse): `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` — и `sys.exit` с понятным сообщением при нарушении.

## MINOR

### m1. Статус verifying нигде не присваивается — мёртвое состояние
team.py:148

Verify принимает статусы `("in_progress", "verifying")`, но присваиваются в файле только `pending` (92), `in_progress` (135) и `completed` (153). В `verifying` не переходит никто — grep подтверждает единственное вхождение слова на 148. Либо состояние забыли реализовать (например, подкомандой submit перед verify), либо его убрали из дизайна, а проверку оставили.

Фикс: убрать `"verifying"` из кортежа на 148 либо добавить переход в него (например, `claim` повторным владельцем или отдельная команда `submit`).

### m2. Claim не сверяет --by с assignee задачи
team.py:133-138, 163

`--by` — свободный текст, движок не проверяет соответствие `t["assignee"]`. Любой агент может забрать чужую задачу под любым именем; при verify fail фидбек уйдёт в mailbox формального assignee (163), а не фактическому исполнителю, и цикл правки заглохнет.

Фикс: в `cmd_claim` проверку `if args.by != t["assignee"]: sys.exit(...)` (при необходимости — флаг `--force` для переназначения).

### m3. Mailbox пишется не атомарно — в отличие от tasks.json
team.py:170, 186, 202 против 47-50

`save_tasks` аккуратно пишет через tmp + `replace`, а все три записи mailbox — прямым `write_text`. Краш в середине записи оставляет битый JSON, после которого `read` (198), `message` (181) и `status` (218) падают JSONDecodeError навсегда, до ручного исправления.

Фикс: вынести `save_json_atomic(path, obj)` (tmp + `Path.replace`) и применять её в шести местах записи: 170, 186, 202 и 49-50.

### m4. cmd_status падает целиком от одного битого mailbox-файла
team.py:218-219

Цикл по `inbox/*.json` делает `json.loads` без обработки ошибок. Один повреждённый или посторонний .json (см. m3 и M4) ломает весь вывод статуса — нельзя увидеть даже список задач.

Фикс: обернуть чтение каждого файла в try/except и печатать `mailbox <имя>: файл повреждён` вместо падения.

### m5. Частично созданный каталог команды даёт противоречивые подсказки
team.py:99-103, 38-39

Если init упадёт после `mkdir` (101-102), но до `save_tasks` (103), останется каталог без tasks.json. Дальше init говорит «каталог команды уже есть» (100), а claim — «команда не найдена… (сначала init)» (39). Обе команды правы по-своему, а выйти из тупика можно только удалив каталог руками.

Фикс: в init проверять не `d.exists()`, а `(d / "tasks.json").exists()` (как в `team_dir`), и при существующем каталоге без tasks.json либо досоздавать структуру, либо сообщать «найден частичный каталог, удалите его».

### m6. --tasks разрешается относительно CWD, а не --project-root
team.py:71-72

`root` берётся из `--project-root`, а `src = Path(args.tasks).resolve()` — от текущего каталога процесса. Остальные команды специально получили `--project-root`, чтобы не зависеть от CWD; init отчасти выпадает из этой схемы: запуск из чужого каталога с относительным путём к спеку упадёт с FileNotFoundError-traceback.

Фикс: `src = Path(args.tasks); src = src if src.is_absolute() else root / src` — или хотя бы clean-ошибка «файл задач не найден: <путь>».

### m7. deps не проверяются на существование при init
team.py:76-97, 118-121

Опечатка в `deps` ("lens-codee") обнаружится только при claim чужой задачи — `find_task` (119) завершит процесс сообщением «задача не найдена». Инвариант «deps ссылаются на существующие id» проверяется в самый поздний момент.

Фикс: в init после построения `seen` проверить `set(t["deps"]) <= seen` для каждой задачи и ругаться сразу со списком битых ссылок.
