### 1. Единый лок — OK

`StateLock` всегда создаёт лок по одному и тому же пути `locks/.state.lock` (team.py:83), то есть все команды сериализуются через один файл. Цикл «чтение → изменение → запись» целиком внутри лока у всех пяти команд из чеклиста:

- claim: вход team.py:178, чтение 179, мутация и запись 187-189, log_event 190;
- verify: вход team.py:200, чтение 201, записи tasks.json 209, 216, 227, запись mailbox (save_mailbox) 218-221 и 230-233 — всё внутри лока;
- release: вход team.py:244, чтение 245, мутация и запись 249-250;
- message: вход team.py:279, save_mailbox 280-282 внутри лока;
- read: вход team.py:294, чтение mailbox 295, отметка «прочитано» 297-298, запись 299.

Оговорка: `tokens --add` тоже мутирует tasks.json, но чтение там вынесено за лок — см. остаточные риски, п. 1.

### 2. Уникальный tmp — OK

team.py:70: `f"{path.name}.{os.getpid()}.{uuid.uuid4().hex[:8]}.tmp"`. Идентификатор процесса плюс 8 hex-символов uuid4 — коллизия имён между двумя записями практически исключена, даже внутри одного процесса.

### 3. Ретрай os.replace — OK

`replace_retry` (team.py:58-66): до 5 попыток с нарастающим ожиданием 0.2-1.0 с, после — финальный вызов, который отдаёт исключение наружу. Вызывается из `write_atomic` (team.py:72), а через него проходят все записи состояния: tasks.json — team.py:166, 189, 209, 216, 227, 250, 264; mailbox — team.py:133, 299. Незащищённых записей состояния мимо этого механизма нет.

### 4. Подбор протухшего лока — OK

team.py:94-99: при FileExistsError считается возраст по mtime файла лока; если он старше `LOCK_STALE_S = 7200.0` (team.py:32, 2 часа), лок удаляется и цикл повторяется — новый захват идёт через `O_CREAT | O_EXCL` (team.py:90), так что из нескольких ожидающих лок получает ровно один. Пока лок свежий, ожидающий спит 0.2 с до дедлайна `LOCK_TIMEOUT_S = 10.0` (team.py:87, 102-104).

## Остаточные риски — что лок НЕ защищает

1. **tokens: чтение и инкремент вне лока.** team.py:258 читает tasks.json без лока, team.py:261-262 меняет `tokens` в памяти, под локом только запись (263-264). Две конкурентные команды `tokens --add` читают один и тот же базовый уровень, и последняя запись затирает прибавку первой (lost update). Кроме того, `log_event` в tokens вызывается вне лока (team.py:265) — единственная команда с таким отклонением от паттерна остальных. Фикс: перенести чтение внутрь `with StateLock`.

2. **Одновременный init.** team.py:162 проверяет `d.exists()`, team.py:164-165 делает `mkdir(parents=True)` без `exist_ok=False`-обработки. Два параллельных init одной команды проходят проверку до создания каталога; второй падает с необработанным `FileExistsError` (трейсбек вместо понятного сообщения), а его `write_atomic` при другом порядке интерливинга мог бы перезаписать чужой tasks.json. StateLock здесь неприменим — каталога и локов ещё нет. Смягчение: `mkdir(exist_ok=True)` с повторной проверкой и отказ до первой записи.

3. **status читает без лока.** team.py:308 (tasks.json) и 315-317 (все mailbox-файлы). Порчи данных нет — атомарная замена файла даёт читателю либо старое, либо новое содержимое, — но status может показать устаревшее состояние на середине чужого перехода. На Windows открытый читатель вынуждает писателя уходить в ретраи `replace_retry` (до ~3 с задержки на каждую запись).

4. **langfuse читает без лока.** team.py:359 (tasks.json), 361 (events.jsonl). Выгрузка строится по снапшоту «на момент чтения»: спаны могут получить неконсистентную комбинацию claimed_at/completed_at (например, claimed_at прошлого круга после release). Мутаций нет, только искажение отчётной картины.

5. **Журнал events.jsonl.** `log_event` (team.py:114-118) — обычный append без лока при вызове из tokens (team.py:265); в claim/verify/release/message журнал пишется внутри лока и сериализован. Параллельные append теоретически могут перемешать строки; выгрузка в Langfuse переживает битые строки (team.py:364-367), но событие при этом теряется из отчёта.

6. **Разбор протухшего лока может сломать взаимоисключение.** team.py:97-99 удаляет лок владельца, который застрял больше 2 часов; team.py:106-111 в `__exit__` удаляет файл по пути без проверки, что это ещё «свой» лок. Если исходный владелец жив и завершится после того, как его лок разобрали и перекрыли, он снесёт чужой свежий лок — в критической секции окажутся двое. Практически недостижимо при критсекциях в миллисекунды и пороге 2 часа; риск появляется только при SIGKILL внутри секции или уходе машины в сон с открытым локом.

7. **Надёжность записи не равна атомарности.** `write_atomic` (team.py:70-72) не делает flush+fsync временного файла перед replace: при сбое питания или ОС результирующий файл может оказаться пустым или замена потеряться. Если финальный `os.replace` в `replace_retry` всё же бросит исключение, временный файл-сирота останется на диске — cleanup в исключительном пути не предусмотрен.

8. **Граница ожидания лока — sys.exit.** team.py:102-103: ожидание дольше 10 с завершает процесс ошибкой. Безопасности это не ломает (задача остаётся доступной), но при плотной конкуренции агент падает вместо ожидания — риск живости, не целостности.

9. **За пределами линзы concurrency.** `cmd_read` не валидирует `--for` (team.py:290: путь `inbox/{args.for_}.json` без `check_name`) — возможный path traversal при чтении mailbox. Относится к чеклисту aud-paths, здесь только фиксируется.

## Итог

Все четыре проверяемых пункта чеклиста — OK. Код соответствует заявленной в docstring модели конкурентности (team.py:11-13) для пяти команд чеклиста. Главная реальная дыра — `tokens --add` с чтением вне лока (риск 1): мутация tasks.json есть, а полного цикла под локом нет. Остальное — чтения без лока (status, langfuse), гонка init и теоретические сценарии после разбора протухшего лока.
